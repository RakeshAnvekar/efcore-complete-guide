# Understanding Distributed Locks vs SemaphoreSlim

## Why Do We Need Locks?

Imagine your application has a product API:

```http
GET /api/products/101
```

The product is cached in Redis.

When the cache expires, many users may request the same product simultaneously.

Without a lock:

```text
1000 Requests
      ↓
1000 Database Calls
```

This can overload the database.

Locks help ensure that only one request loads data from the database while the others wait.

---

# SemaphoreSlim

## What is SemaphoreSlim?

`SemaphoreSlim` is an in-memory synchronization mechanism.

Example:

```csharp
private static readonly SemaphoreSlim _lock =
    new SemaphoreSlim(1, 1);
```

Meaning:

```text
Only 1 request can enter.
All others wait.
```

---

## Single Server Example

```text
Users
  ↓
ASP.NET Core API
  ↓
SemaphoreSlim
  ↓
Database
```

### Request Flow

```text
Request 1
    ↓
Gets Lock
    ↓
Database Call
    ↓
Updates Cache
    ↓
Releases Lock

Request 2
    ↓
Waits
    ↓
Reads Cache

Request 3
    ↓
Waits
    ↓
Reads Cache
```

Result:

```text
100 Requests
      ↓
1 Database Call
      ↓
99 Cache Reads
```

Perfect.

---

# The Problem With SemaphoreSlim

SemaphoreSlim only works inside a single application process.

Suppose your application is scaled out.

```text
                Load Balancer
                      |
      --------------------------------
      |              |              |
   Server 1       Server 2       Server 3
```

Each server has its own memory.

Each server creates its own SemaphoreSlim.

```text
Server 1
  └── SemaphoreSlim

Server 2
  └── SemaphoreSlim

Server 3
  └── SemaphoreSlim
```

These locks do not know about each other.

---

## What Happens?

Suppose cache expires.

Requests arrive:

```text
User 1 → Server 1
User 2 → Server 2
User 3 → Server 3
```

All servers get cache miss.

```text
Server 1 → Database
Server 2 → Database
Server 3 → Database
```

Result:

```text
3 Database Calls
```

If you had:

```text
10 Servers
```

Then:

```text
10 Database Calls
```

SemaphoreSlim cannot protect across multiple servers.

---

# What is a Distributed Lock?

Instead of storing the lock in application memory, store the lock in a shared location.

Example:

```text
Server 1
Server 2  -----> Redis
Server 3
```

Now every server checks the same lock.

---

## Shared Lock Concept

Redis stores:

```text
lock:product:101
```

This is the shared lock.

All servers look at the same lock.

---

## Flow

### Step 1

Server 1 asks Redis:

```text
Can I get lock:product:101 ?
```

Redis:

```text
Yes
```

Server 1 proceeds.

```text
Server 1 → Database
```

---

### Step 2

Server 2 asks Redis:

```text
Can I get lock:product:101 ?
```

Redis:

```text
No
```

Server 2 waits.

---

### Step 3

Server 3 asks Redis:

```text
Can I get lock:product:101 ?
```

Redis:

```text
No
```

Server 3 waits.

---

### Step 4

Server 1 completes work.

```text
Database Read
     ↓
Cache Updated
     ↓
Lock Released
```

Redis removes:

```text
lock:product:101
```

---

### Step 5

Server 2 retries.

Now cache exists.

```text
Redis Cache
     ↓
Product Found
```

No database call.

---

## Result

Without Distributed Lock:

```text
3 Servers
     ↓
3 Database Calls
```

With Distributed Lock:

```text
3 Servers
     ↓
1 Database Call
     ↓
2 Cache Reads
```

# Real-Life Analogy

Imagine three bank branches.

```text
Branch A
Branch B
Branch C
```

All need approval from Head Office.

Head Office keeps one approval token.

```text
Head Office
     |
Approval Token
```

### Branch A

Takes token.

```text
Branch A → Working
```

### Branch B

Cannot get token.

```text
Branch B → Wait
```

### Branch C

Cannot get token.

```text
Branch C → Wait
```

When Branch A returns token:

```text
Branch B → Proceed
```

In this analogy:

```text
Head Office = Redis
Approval Token = Distributed Lock
Branches = Application Servers
```

# How Redis Creates a Lock

Redis command:

```redis
SET lock:product:101 unique-id NX EX 30
```

Explanation:

| Option | Meaning |
|----------|----------|
| NX | Create only if key does not exist |
| EX 30 | Expire after 30 seconds |
| unique-id | Owner identifier |

---

## Server 1

```redis
SET lock:product:101 abc123 NX EX 30
```

Result:

```text
OK
```

Lock acquired.

---

## Server 2

```redis
SET lock:product:101 xyz789 NX EX 30
```

Result:

```text
NULL
```

Lock not acquired.

---

# RedLock

RedLock is a distributed locking algorithm built on Redis.

Instead of one Redis instance:

```text
Redis 1
Redis 2
Redis 3
Redis 4
Redis 5
```

A lock is considered valid only if a majority agree.

Example:

```text
3 out of 5 Redis Nodes
```

This provides better reliability in distributed systems.

# Comparison

| Feature | SemaphoreSlim | Distributed Lock | RedLock |
|----------|--------------|------------------|----------|
| Single Server | ✅ | ✅ | ✅ |
| Multiple Servers | ❌ | ✅ | ✅ |
| Stored In Memory | ✅ | ❌ | ❌ |
| Uses Redis | ❌ | Optional | ✅ |
| Async Support | ✅ | Depends | ✅ |

# Interview Answer

### What is SemaphoreSlim?

SemaphoreSlim is an in-memory synchronization primitive used to limit concurrent access within a single application instance. It supports async/await and is commonly used to prevent cache stampede on a single server.

### What is a Distributed Lock?

A distributed lock stores lock information in a shared system such as Redis. Multiple servers coordinate using the same lock, ensuring that only one server performs a critical operation at a time.

### What is RedLock?

RedLock is a Redis-based distributed locking algorithm that improves lock reliability by coordinating lock acquisition across multiple Redis nodes.
